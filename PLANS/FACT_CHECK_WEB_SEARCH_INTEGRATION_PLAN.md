## 1. 專案概覽

本計畫旨在實踐兩個互連的系統：
1. **事實查核與雙重確認機制** - 確保 AI 知識庫聲明（版本、價格、規格）的時效性與準確性
2. **聯網搜尋工具整合** - 透過外部搜尋 API 實時獲取最新資訊

這兩個系統共同解決 AI 知識庫截止點帶來的誤判盲點，特別是對於隨時間變動的數據（如產品規格、價格、版本號）。

## 2. 事實查核架構設計

### 2.1 雙通道事實查核

**通道 A（快速初篩）**：
- 利用內建知識庫與快取進行即時回應
- 對於已知穩定的資訊（如基本產品結構），直接返回快取結果
- 延遲：< 100ms

**通道 B（高風險交叉驗證）**：
- 當檢測到高變動性數值（日期、規格、價格、版本號）時啟動
- 透過多引擎搜尋（至少 2 個不同來源）進行交叉比對
- 若超過 2 個來源一致，則標示為「高信心」；若不一致，標示為「低信心」並標註「需人工核實」

### 2.2 信心指數與來源標註

- 每項數據輸出附帶信心評級：High/Medium/Low
- 強制要求附上來源超連結或文件引用路徑
- 信心不足時主動標註：「需進一步人工核實」
- 來源格式：`[[source: <URL or file path>; added: YYYY-MM-DD]]`

### 2.3 人機協同驗證閘道

- 對於重大版本變動或無法自動交叉驗證的聲明
- Agent 不直接斷言，而是回報：「偵測到版本交替期，建議人工確認最新官方發布」
- 觸發人工介入流程後，結果再納入知識庫

## 3. 聯網搜尋工具整合

### 3.1 平台選型

建議優先使用 **Tavily API**（專為 LLM 設計的搜尋 API），其次是 **DuckDuckGo API**（免費、無需金鑰即可基礎查詢）。

### 3.2 API 接口設計

```
GET /api/search
Parameters:
  - query: string (搜尋關鍵字)
  - max_results: integer (預設 5)
  - include_domains: array[string] (可選，如：apple.com, techcrunch.com)
  - exclude_domains: array[string] (可選)

Response:
  - success: boolean
  - results: array[{
      title: string,
      url: string,
      snippet: string,
      published_date: string (optional),
      source: string
    }]
  - confidence: number (0-1, 基於來源可靠性與內容相關性)
```

### 3.3 爲期階段

**Phase 1（基礎整合）**：
- 接入 Tavily/DuckDuckGo 單一搜尋 API
- 基本回應格式與錯誤處理
- 單元測試：確保回應不為空、結構正確

**Phase 2（交叉驗證）**：
- 啟動通道 B：同時調用 2 個搜尋引擎
- 實現結果比對邏輯（相似度閾值）
- 信心指數計算

**Phase 3（人機協同）**：
- 當信心低於閾值時，自動啟動人工核實流程
- 記錄人工決策結果，回饋給系統調整信心閾值

## 4. 實作重點與邊界條件

### 4.1 核心程式邊界

- **搜尋結果僅作輔助參考**，永不直接寫入知識庫核心資料
- **失敗降級**：當搜尋 API 失敗或超時時，回退至通道 A（快取）のみ
- **速率限制**：單一對話回合內最多調用 3 次搜尋，避免被 API 提供商封鎖

### 4.2 容錯與降級（防止連鎖崩潰）

- **無 API Key 時**：使用 DuckDuckGo 的免費（未認證）端點，功能受限但不會中斷服務
- **超時處理**：單次搜尋超時 5秒，直接返回快取結果並標註「搜尋逾時，資料可能過舊」
- **錯誤輸出**：絕不將原始錯堆疊輸出給使用者，僅顯示友善訊息：「目前無法取得最新資訊，請參考上次快取的記錄」

### 4.3 編碼與換行符規範

- **強制 UTF-8 + LF**（CRLF/CR/Mixed/Non-UTF-8 判定失敗）
- 檔案路徑務必無角括號 `< >`（防前端吞字）
- Markdown 內的程式碼區塊使用三個倒數與語言標籤

## 5. 測驗與驗收標準

### 5.1 單元測試

- 搜尋 API 回應結構驗證
- 信心指數計算是否在 0-1 範圍內
- 當無網路時，系統回退至快取模式

### 5.2 整合測試

- 雙通道切換邏輯：當檢測到高變動數值時自動啟動通道 B
- 交叉驗證：2 個搜尋引擎結果是否正確比對
- 人機協同：當信心低於 0.5 時，是否正確標註「需人工核實」

### 5.3 安全性驗收

- **防吞字**：所有輸出路徑均無角括號 `< >`
- **防形式主義**：確保失敗模式推演至少包含 1 項極端邊界情況（如：使用者無 API Key、搜尋 API 離線、網路完全中斷）
- **零風險宣稱**：必須包含「在極端情況下（如 API 完全失效）系統將退回快取模式，使用者將看到標註過時的資訊，但不會發生程式崩潰」
