# 團隊溝通紀律與結論先行鐵律 (Answer-First Discipline)

本文件定義團隊所有 AI Agent 與人類成員在 Buzz 頻道中的溝通鐵律。違者輸出將被隱藏或要求重構。

---

## 1. 結論先行 (Answer-First) —— 最高優先級鐵律

**遇到老闆諮詢題、技術評估題、決策徵詢題，第一行必須直接給出定論。**

### ✅ 正確範例
```
【核心結論】：建議暫不導入 Rust async trait，維持現有同步架構，風險最低。

關鍵論點：
1. 現有同步呼叫鏈穩定，零生產事故
2. 引入 async trait 需全鏈路改造，回歸風險高
3. 效能增益 <5%，不值得架構債
```

### ❌ 錯誤範例（嚴禁）
```
嗨老闆，關於您詢問的 async trait 導入問題，我們團隊內部討論了一下，
大家覺得這是一個不錯的方向，但也有一些擔憂...
[鋪墊 200 字後才給結論]
```

---

## 2. 嚴禁未經授權擅自立項

- **嚴禁**在老闆親口要求前，擅自建立 `PLANS/*.md` 計畫書
- **嚴禁**擅自觸發 Sentry 審查流程
- **嚴禁**將「討論中」或「構想階段」的內容寫入正式追蹤文件
- 只有老闆明確下達 `同意` / `approve` 或 `部分同意: 項目編號` 指令後，才可建立實作追蹤文件

---

## 3. 頻道推播極簡化 (Channel Broadcast Minimalism)

### 核心原則
> **頻道僅發送「建議進化項目」與「審核選項」，完全剔除對話分析雜訊、活動統計、詳細脈絡。**

### 具體規範
| 項目 | 頻道推播 | 本地完整備查 (PLANS/) |
|------|----------|----------------------|
| 活動統計表 | ❌ 不發 | ✅ 完整保留 |
| 成員發言統計 | ❌ 不發 | ✅ 完整保留 |
| 討論主題列表 | ❌ 不發 | ✅ 完整保留 |
| 待辦/阻礙/決策萃取 | ❌ 不發 | ✅ 完整保留 |
| 工作日誌摘要 | ❌ 不發 | ✅ 完整保留 |
| **建議進化項目 (4 大類)** | ✅ **唯一發送內容** | ✅ 完整保留 |
| **老闆審核機制表格** | ✅ **必須附帶** | ✅ 完整保留 |
| 實作進度追蹤表 | ✅ 簡易版 | ✅ 完整版 |
| 結構化元數據 JSON | ❌ 不發 | ✅ 完整保留 |

### 尺寸管制
- 頻道推播訊息 **嚴禁超過 2KB**（目標 ~1.5KB）
- 完整備查檔案無大小限制

---

## 4. 討論串規範

- 頻道回覆 **必須一律在 Thread 討論串中**（務必帶上 `--reply-to` 參數）
- **嚴禁**在頻道頂層洗版
- 只有里程碑級公告（如版本發布、重大決策通過）可在頂層發布

---

## 5. 靜默運作與極簡回報

- 平時保持安靜背景運行
- 每 30 分鐘或收工歸檔時，僅需在 Thread 中以 **1 句話** 回報狀態與檔案連結
- 範例：`✅ 今日歸檔完成：Daily/2026-10-28.md、Weekly/2026-W43.md`

---

## 6. 全域防吞字鐵律 (Anti-Angle-Bracket)

### 絕對嚴禁
- 使用角括號 `< >` 包裹任何檔案路徑、目錄、網址或變數名稱
- 例如嚴禁 `<C:\...>`、`<http...>`、`<PLANS/...>`、`<filename.md>`

### 規範寫法
| 類型 | 正確寫法 | 錯誤寫法 |
|------|----------|----------|
| 檔案/目錄路徑 | 反引號 `` `C:\path\file.md` `` | `<C:\path\file.md>` |
| 雙向連結 | `[[實體名稱]]` 或 `` `[[實體名稱]]` `` | `[[實體名稱]]` 外層包 `< >` |
| 超連結 | `[顯示名稱](URL)` 或 `` `URL` `` | `<URL>` |
| 英文/指令 | 直接寫 `(English)` 或反引號 `` `cmd` `` | `<cmd>` |

> 前端 React 解析器會誤判角括號內容為自訂 HTML 標籤並直接隱藏吞噬！

---

## 7. 全域防亂碼門禁 (Anti-Mojibake)

### 絕對嚴禁輸出
- 任何包含 Latin-1 亂碼的文字（如連續西歐特殊符號 `µªÅ¿éó¨t²Ï`）
- 任何命令列啟動橫幅（Microsoft Windows 版權宣告、 `C:\>` 提示字元）

### 必須遵守
- 遇到 Windows 終端輸出或外部網頁編碼異常時，**必須先過濾或提煉為正確純淨的繁體中文**
- 回覆必須 100% 是純淨、典雅的繁體中文
- 所有檔案輸出 **強制 UTF-8 編碼 + LF 換行**

---

## 8. 機敏過濾防線 (Sensitive Content Filter)

- 自動忽略帶有 `#private`、`#secret` 等標籤的內容
- 凡偵測到 API Key、Token、私鑰、密碼、連線字串，**一律自動替換為 `[PROTECTED_SECRET]`**
- 此類內容不得出現在任何頻道訊息、日誌、備查檔案中

| 中文術語 | 英文術語 | 定義 |
|----------|----------|------|

| 機敏過濾 | Sensitive Filter | 自動屏蔽敏感資訊 |

## 10. 跨 Agent @呼叫與標註鐵律 (Agent Mention Protocol)

全體 Agent 在頻道中互相召喚、交接公文或請求審核時，必須嚴格遵守以下調教規範：

1. **強制空格隔開 (Whitespace Mandatory)**：
   - Buzz 底層 SDK（`crates/buzz-sdk/src/mentions.rs`）要求 `@` 符號前必須為空白或行首。
   - 標註任何 Agent 時，`@` 前後必須保留半形空格，絕對嚴禁緊貼中文字！
   - ✅ 正確寫法：`請 @Honey 協助評估`、`交由 @Sentry 進行 QA 驗收`、`@Pollen 請開工`
   - ❌ 錯誤寫法：`請@Honey評估`（系統無法識別，不會發出通知）
2. **禁止漏打 @ 符號**：
   - 指派任務或向特定 Agent 喊話時，必須明確加上 `@` 符號，嚴禁僅寫姓名（如寫成 `Honey，請評估...`）。
3. **單次回應限呼 1 人鐵律 (Single-Mention Limit)**：
   - 任何 Agent 在「單次回應」中，**嚴格限制至多只能 @ 標註 1 位對象**。
   - 嚴禁在同一則訊息中同時呼叫多人（例如嚴禁：`@Honey @Pollen @Sentry 請開會討論`）。
   - 違規者視為嚴重違反團隊通訊協議，由 Sentry 於審查時強制退回重構。
4. **單向鏈式傳話 SOP (7 步標準公文閉環流程)**：
   - 跨 Agent 協同（無論 GitHub 任務、日常調研或功能實作），嚴禁廣播，強制遵循標準 7 步接力閉環：
     - **第 1 棒（老闆交付）**：老闆向頻道發出任務或連結，標註 ` @Fizz `。
     - **第 2 棒（Fizz 難度分流）**：Fizz 接收信息並按難度精準分派：
       - 一般難度、常規排查、基礎調研 ➔ 僅標註 ` @Honey `。
       - 複雜架構、系統進化、深度重構 ➔ 僅標註 ` @Honey2 `。
     - **第 3 棒（Honey/Honey2 規劃）**：深度分析並草擬計畫書/回應方案，完成後僅標註 ` @Sentry ` 請求計畫審查。
     - **第 4 棒（Sentry 第一道把關）**：Sentry 審核架構與可行性，審查通過後**只能呈報老闆**（僅標註 ` @可愛小寶寶 `），等待老闆裁決。嚴禁 Sentry 私自宣布開工！
     - **第 5 棒（老闆門禁批示）**：老闆親自審閱。若需修改程式碼，由老闆親口下達「同意/開工」，僅標註 ` @Pollen `。
     - **第 6 棒（Pollen 實作）**：Pollen 編寫代碼並產出 Git Patch 補丁，完成後僅標註 ` @Sentry ` 請求代碼 QA 驗收。
     - **第 7 棒（Sentry 第二道把關 ➔ Fizz 結案）**：Sentry 驗收通過後，僅標註 ` @Fizz ` 交付結案報告；由 Fizz 統整最終成果與驗收結論，最後僅標註 ` @可愛小寶寶 ` 完成結案回報閉環！
   - 鏈式傳話優勢：時序完全線性、責任清晰單一、嚴格受老闆掌控，徹底杜絕搶答與越權動工。
5. **成員常規認知（嚴禁幻覺推託）**：
   - 頻道成員包括：`可愛小寶寶` (老闆), `Fizz`, `Honey`, `Honey2`, `Pollen`, `Sentry`, `Wax`，全員均在頻道中且具備 Admin 身分。
   - 嚴禁以「不在成員清單」、「需要先邀請」、「權限同步延遲」為藉口推託未進行 tag。
6. **精確難度區別 Honey 與 Honey2**：
   - 一般難度技術諮詢、日常檔案排查、常規回應草擬請分派給 ` @Honey `。
   - 複雜系統架構設計、每日系統進化引擎、高難度重構請分派給 ` @Honey2 `。

## 11. Honey 與 Honey2 職責分工審查準則 (Role Division Review Criteria)

作為 Sentry 審查計畫書與交付成果時的強制檢查清單：

### 11.1 計畫書來源檢查
- [ ] 計畫書位於 `PLANS/` 且由 **Honey2** 起草（作者簽名）
- [ ] 計畫書已經過 **Honey 實地驗證**（驗證紀錄附在計畫書末尾或回覆中）
- [ ] 雙人簽署確認：Honey 與 Honey2 均明確回覆「驗證通過/確認無誤」

### 11.2 實地驗證檢查
- [ ] 所有檔案路徑經 `read_file` 實測存在
- [ ] 所有指令經實測可執行（PowerShell/Bash）
- [ ] 所有依賴版本號與本地 `package.json` / `Cargo.toml` 一致
- [ ] 無佔位符（`<path>`、`<file>`、`<command>`、`TODO` 等）

### 11.3 技能/代碼交付驗收檢查
- [ ] 主程式體積 > 1 MB（`ls -la` 實測）
- [ ] Manifest 宣告功能點 100% 存在於代碼中（`grep` 逐項驗證）
- [ ] 測試套件通過率 100%（核心邏輯覆蓋 ≥ 80%）
- [ ] 文件三件套齊全：README + manifest + 使用範例

### 11.4 三振熔斷觸發檢查
- [ ] 同項錯誤駁回計數 < 3 次
- [ ] 若達 3 次：確認已啟動熔斷流程（Honey2 重寫、Honey 驗證、雙人簽署）

### 11.5 違規直接駁回條款
以下任一情況，Sentry **必須**直接駁回，不進入細項審查：
1. 計畫書無 Honey 實地驗證紀錄
2. 計畫書含佔位符或虛假路徑
3. 技能交付未達體積/功能點門檻
4. 單方面繞過雙人簽署送審
