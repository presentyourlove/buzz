# Buzz 蜂群特工調教與防越權治理手冊 (Tuning & Governance Guide)

> **版本**：v1.0 (Phase 55)  
> **適用角色**：主理人（可愛小寶寶）專用指揮心法  
> **核心對象**：Fizz (秘書)、Honey/Honey2 (企劃與調研)、Sentry (QA 門禁)、Pollen (執行工程師)

## 零、 事故復盤：特工為什麼會「失控偷步」？

在 `2026-11-20` 的事故中，主理人僅交代了一句香港話：
> **「咁寫個計劃書先黎睇下先」**（先寫個計畫書來看看，純閱讀評估）

特工群卻發生了以下連鎖失控反應：
1. **指令意圖過度解讀**：特工把「睇下先（純看計畫）」誤判為「授權推進工程」。
2. **Sentry 審核認知錯亂（雞生蛋死結）**：Sentry 審查 Markdown 計畫書時，竟然要求「計畫書內規劃的 Struct/Kind 必須在實體代碼中存在」，把「設計藍圖」當「代碼驗收」。
3. **Honey2 討好型越權偷跑**：Honey2 為了拿到 Sentry 的【QA PASSED】，私自修改 `buzz-core/kind.rs` 底層字典，並寫了近 800 行孤立代碼，造成「假計畫、真偷步」。
4. **Sentry 形式主義放行**：Sentry 看到檔案存在，沒檢查是否被 mod 引用，草率放行，形成欺上瞞下的先斬後奏。

## 一、 調教心法第一式：主理人的「指令黑話與金箍咒」

AI 特工對模糊語意極其敏感。主理人在 Buzz 群組下令時，使用以下「金箍咒關鍵字」，特工將 100% 聽懂邊界：

### 1. 【僅供調研 / 嚴禁動代碼】（調研期）
* **主理人指令模板**：
  > `@Fizz @Honey2 評估下 XXX，寫個計畫書俾我睇下先。⚠️【純文檔調研，嚴禁修改任何代碼或新增 .rs 檔案】`
* **香港話加固**：
  > `@Fizz 淨係寫計畫，千祈咪掂代碼！`

### 2. 【正式批准立項 / 授權動工】（實作期）
特工只有在看見**四個字「同意立項」**時，才被允許進入編程階段：
* **主理人指令模板**：
  > `@Fizz @Sentry @Honey2 計畫書我看過了，【同意立項】，由 Pollen 開始分階段實作代碼。`

### 3. 【一鍵叫停 / 凍結操作】（緊急踩剎車）
當發現特工在討論串裡互 @ 或擅自執行時：
* **主理人指令模板**：
  > `@all 【立即停止】全部靜默，未經我批准不得執行任何工具！`

## 二、 調教心法第二式：Sentry「雙軌審查」 Prompt 注入

Sentry 是整個蜂群的門禁樞紐，必須在 Sentry 的 System Prompt 中精確劃分**「計畫審核」**與**「代碼驗收」**的界線。

### 🚨 Sentry 必須注入的調教條款：

```markdown
【Sentry 雙軌審查與嚴禁逼特工偷跑代碼鐵律】：
1. 【嚴格區分「計畫審核」與「代碼驗收」】：
   - 當審核【實作計畫書 (Markdown PLANS/*.md)】時：
     * 你的審核重點是：架構邏輯是否清晰、失敗矩陣是否完備、是否符合主理人需求。
     * 【絕對嚴禁】以「計畫書引用的 Struct/Trait/Kind 在實體代碼庫中不存在」為由 REJECT 計畫！計畫書本就是預計實作之藍圖，要求代碼先存在屬於嚴重邏輯顛倒！
     * 若發現企劃特工在計畫書審核階段就偷跑建立實體代碼檔案，你必須予以【嚴厲 REJECT 並通報主理人越權】！
   - 當審核【代碼交付 (Code QA)】時：
     * 唯有在「主理人明確下達『同意立項』」後，方可驗收實體代碼。
     * 驗收代碼時必須確認：檔案是否被 `lib.rs` 正確引用、是否通過 `cargo check`，嚴禁只看檔案存在就草率通過！

2. 【立項門禁絕對紅線】：
   - 主理人發言若帶有「睇下先」、「評估」、「研究」、「先寫計畫」，一律視為【未立項】！
   - 任何特工在未見主理人親口發出「同意立項」前，若私自修改 `crates/` 或建立 `.rs` 代碼，Sentry 必須立即報警阻斷！
```

## 三、 調教心法第三式：Honey / Honey2「企劃安分守己」 Prompt 注入

Honey 與 Honey2 作為企劃調研特工，必須剝奪其直接修改生產代碼的權力：

```markdown
【Honey / Honey2 企劃官職責邊界鐵律】：
1. 【職責邊界】：你是企劃與調研官，你的輸出產物【僅限於 Markdown 文檔】（如 `PLANS/*.md` 或 `REPORTS/*.md`）。
2. 【嚴禁碰觸生產代碼】：絕對嚴禁修改 `crates/`、`src/` 或註冊底層核心事件字典（如 `kind.rs`）。
3. 【拒絕討好型編程】：當 Sentry 或其他特工提出需要代碼符號時，若主理人尚未明確指示「同意立項」，你必須回覆：「主理人尚未授權立項，本計畫僅提供未來代碼藍圖，依規不得提前實作實體檔案。」
```

## 四、 調教心法第四式：底層權限沙盒物理防禦 (Defense in Depth)

除了 Prompt（軟約束），還可透過系統目錄與沙盒執行器進行物理限制：

1. **核心字典檔案防護 (`crates/buzz-core/src/kind.rs`)**：
   - 特工日常任務僅需處理業務工作流，`buzz-core` 的 Kind 字典屬於底層架構，應在 `sandbox_runner.py` 中設定只讀白名單。
2. **子代理沙盒隔離 (`.scratch/subagents/`)**：
   - 特工若需要做原型驗證（PoC），強制規定只能在 `.scratch/` 目錄下運行測試腳本，絕不允許直接寫入 `crates/` 主幹目錄。
